# STC 从 Deno 迁移到 Node.js 的计划

日期：2026-10-11  
状态：本机实现与验证已完成，全平台 CI 和真实发行验收待执行。详见 [验证记录](nodejs-migration-validation.md)。

## 目标与范围

将 STC 的开发、测试、构建、CI 和发布迁移至 Node.js，使 npm 包和 Node CLI不再依赖 Deno。保持现有转换结果和插件契约，避免在迁移中混入生成逻辑重构或新功能。

基线为 Node.js 24 LTS、TypeScript 和 ESM，交付 npm 包与 Node CLI。Bun 作为后续兼容验证对象。

Deno 团队在 2026-10-09 公告中表示，将继续提供一年每月的错误修复和安全更新，之后结束团队对运行时的开发；项目仍然开源。因此本计划用于主动迁移，并非处理已经不可用的运行时。参见 [Deno 官方公告](https://deno.com/blog/cloudflare) 和 [Node.js 发布状态](https://nodejs.org/en/about/previous-releases)。运行时版本与依赖版本在实施时再次确认。

## 当前项目基线

| 范围           | 当前实现                                                          | 迁移关注点                                 |
| -------------- | ----------------------------------------------------------------- | ------------------------------------------ |
| 入口与转换管线 | `src/main.ts` → `src/cli.ts` → `src/app.ts`，公开入口为 `mod.ts`  | 保持参数行为、公开导出和插件生命周期       |
| 文件操作       | `src/utils.ts` 使用 Deno API 与 `@std/fs`                         | 文件编码、目录清理、差异写入和 `.stc.lock` |
| 配置           | `src/config.ts` 支持 JSON、JS、TS 配置，动态导入绕过缓存          | TS 加载、配置依赖、相对路径和重载          |
| 监听           | `src/watcher.ts` 使用 `Deno.watchFs` 和信号监听                   | 防抖、文件替换、失败恢复和退出清理         |
| 资源           | `src/pack.ts` 将模板和 shared 内容生成到各插件的 `index.ts`       | 资源完整性、构建完成顺序和安装后路径       |
| npm 构建       | `src/npm/build.ts` 使用 `dnt`，启用 Deno shim，关闭类型检查与测试 | 原生 Node 构建、类型声明和真实安装包验证   |
| CI 与发行      | `.github/workflows/check.yml`、`npm.yml`、`deno-build.yml`        | Node 检查、版本来源、发布触发和 JSR 去向   |

## 必须保持的行为

- OpenAPI/Swagger v2、v3，远程与本地输入，JSON 与 YAML 解析。
- TypeScript、JavaScript、Dart、Swift、MCP 插件，以及第三方插件接口。
- `start`、`defineConfig` 和现有插件子路径导出。
- CLI 选项、别名、默认值和显式布尔值；CLI > 配置文件 > 默认值的优先级。
- 配置文件查找顺序，以及配置中的本地路径相对配置文件目录解析的规则。
- `.stc.lock`、差异写入、清理规则、shared 输出和 `noDeprecated`。
- watch 的首次生成、配置重载、远程轮询和首次失败后继续监听。
- 中英文日志和错误反馈。

`shared/` 与 `template/` 继续排除在通用格式化和 lint 之外。核心解析和模板内容的变化应有独立理由及回归证据。

### 3. 替换运行时与依赖

| 当前依赖或 API               | 迁移方向                               | 验证要求                         |
| ---------------------------- | -------------------------------------- | -------------------------------- |
| Deno 文件 API、`@std/fs`     | `node:fs/promises`，必要时配合 glob 库 | 编码、异常、目录语义和写入行为   |
| `@std/path`                  | `node:path`、`node:url`                | Windows 路径、空格、文件 URL     |
| `Deno.args`、`cwd`、`exit`   | Node `process` API                     | 参数切片、退出码和异步清理       |
| `@std/cli`                   | Node 参数解析或 npm 参数库             | 别名、多值、未知选项和显式 false |
| `@std/fmt`、datetime、进度条 | Node/npm 对应实现                      | 日志、时间格式和非交互终端       |
| JSR、URL 模块导入            | npm 包或 Node 内置模块                 | 版本对齐、默认导出和 ESM 兼容    |

- [x] 先迁移公共工具，再迁移 CLI、配置、监听和构建入口。
- [x] 保持 Eta 模板语义，核实不同入口的 Eta 版本使用情况。
- [x] 核实 `oxc-transform` 原生依赖在目标平台的加载与打包。
- [x] 检查运行时代码不再残留 Deno API、Deno shim 或仅 Deno 可解析的模块地址。

验收：Node CLI 和库入口能完成一次完整生成；无需 Deno 安装或运行时兼容层。

## 发布与回退

- 保留迁移前版本与发行产物，使用独立预发布版本验证新工具链。
- 预发布验证覆盖源码运行、npm tarball 安装和 Node CLI。
- 正式发布前记录最低 Node 版本、模块兼容、配置行为和安装方式变化。
- 失败时将 npm 默认发布标签恢复到已验证旧版本；保留问题版本和诊断信息。
- 旧 Deno 版本作为过渡回退入口，不视为长期维护方案。
